# game-review Skill

狙いは「前回から何が良くなり、何が動いていないか」を数字と根拠で示し、次にやることを絞ること。
**レビュー自体はコードも仕様書も変えない。**改善案はすべて提案(未確定)として扱う。

## 置き場所

- レビュー文書: `scratchpad/reviews/Review_100points_YYYY-MM-DD.md`(プロジェクト直下の `scratchpad/` はgitignore済み。
  docs直下は9ファイルの決まりがあるのでdocsへは置かず、commitもしない)
- 材料(brief): このセッションのスクラッチパッド
- 前回のレビュー: `scratchpad/reviews/` の最新の1本。無ければ下の「標準のレビュアーと観点」で新しく始める

## モデルの使い分け

| 段 | 担当 |
|---|---|
| 1. 材料集め(3本を並行) | Sonnet のサブエージェント。読み取りと集計だけ |
| 2. 採点と執筆 | Opus のサブエージェント(またはこのセッションがOpusなら自分) |
| 3. 検品・報告 | このセッション |

各サブエージェントには「リポジトリのファイルを変更・commitしない」「`bash tools/check.sh` は gdformat が
ファイルを書き換えるので実行しない」「最終報告はファイルを書けたかと3行の要約だけ」を必ず書く。

## 1. 材料を集める(Sonnet ×3、並行)

書き出し先はスクラッチパッド。それぞれ150〜200行以内、数字と出どころ(コミットID・ファイル名)を添え、推測は推測と明記させる。

- **brief_data.md(実プレイの数字)**: `tools/analyze_matches.py` を直近30日と直近7日で回す(使い方は先頭のdocstringと
  `docs/BalanceReport_v5.md`)。起動→誘導対局開始→ホーム→誘導対局を終えた/飛ばした→CPU戦完走→遠征(開始・3段目・踏破・2回目)→
  オンライン入口・対戦完了→別の日に来た、誘導対局の手順ごとの通過、ランク待機(当たれた割合・自分でやめた割合)、
  オンラインの局数・先手勝率・決着手数・時間中央値・投了率・時間切れ率、カード別の使用率・勝率の上位下位。
  `BalanceReport_v5.md` から自己対戦の逆転率・先手勝率・平均手数の現行値と目標値。前回の表があれば同じ項目を並べる。
  認証が足りず回せなければ回避せず「何が足りなかったか」を書く。Windowsの端末では出力が文字化けするので
  `python -X utf8` かファイル出力で読む
- **brief_changes.md(前回以降の変化)**: 前回レビューの日付以降の `git log` をテーマ別(カード・対局の手触り・各画面の磨き込み・
  誘導対局・遠征・オンライン/ランク・性能/pck・砂時計の描画・運営/告知/ショート・道具/検査)に件数つきで要約。
  前回のP0/P1/P2と目立つ改善案の「実施済み/一部/未着手」表。`docs/TODO.md` の残り、`docs/UiPolishLog.md` の判定待ちと候補、
  `docs/NextCardSet.md` の状況。`docs/Hourglasses.md` からカード総数・セット別枚数・直近セットの一覧。
  `docs/GameDesign.md` の索引からモードと機能の一覧(1行ずつ)
- **brief_code.md(コードと品質)**: `scripts/` `scenes/` `tools/` の規模、行数上位15本(900行超に印)、テストの本数と対象、
  `tools/check.sh` の段、テストが薄い領域の推定、`docs/arch/` の層の分け方、`docs/Pitfalls.md` の代表5件、
  `git status` と未コミットの変更の要点、直近の性能・容量の取り組みと数字、オンラインの方式と計測イベント、
  アクセシビリティと設定(無いものは「見当たらない」)、運営のSkillとビルド頻度、TODO/FIXME/HACKの数

## 2. 採点して書く(Opus)

材料3本と前回レビューを読ませ、足りない根拠だけ `docs/design/` `docs/arch/` コードを必要な範囲で読ませる(読み過ぎない)。

### 文書の構成

- `# 砂時計アリーナ レビューと改善案(10人×10観点 / 1000点)— YYYY-MM-DD`
- `## 前提`: 仮想レビュアーであること、根拠にしたもの、実機の画面は見ていないこと、母数が小さい数字の注意
- `### 直近30日の主要な数字`: 前回値・今回値(・直近7日)の表
- `### 前回以降に変わったこと`: 5〜8行
- `## 総評: **NNN / 1000点**(前回NNN)`: 3〜5行と、レビュアー別の点の表(前回・今回・増減)
- `## A.`〜`## J.`: `|#|観点|点|良かったところ|ダメだったところ|具体的な改善案|` を10行ずつ。点は `7(+1)` のように増減を添える
- `## 次の改善案(優先順)`: P0(今週。3〜4個)/ P1(次の2週間)/ P2(次にプールを触る回)/ 判断が必要なもの(ユーザーにしか決められない)。
  各項目に、狙う数字・やること・規模(小/中/大)・由来のマス(例: A2, J4)
- `## 前回の改善案の行方`: 前回のP0/P1/P2の実施済み/一部/未着手

### 採点と中身の決まり

- **レビュアー・観点は前回をそのまま引き継ぐ**(点の増減を比べるため)。前回が無いときだけ下の標準を使う
- **100マスすべてに、そのマス固有の良かったところ・ダメだったところ・具体的な改善案を1つずつ。**一般論(「テストを増やす」)や
  使い回しは不可。改善案は「どの画面/どのファイル/どの数字を、どう変えるか」まで。1セル1〜2文
- 点は根拠で動かす。実際に入った仕組み・UiPolishLog で採用になった変更・動いた数字で上げる。
  **実機の画面を見ていないので、見た目の良し悪しそのものでは大きく上げない。**数字が動いていないマスは据え置きか、
  提案済みで未着手なら下げてよい
- 合計は各マスの積み上げで出して検算する(10マスの和=レビュアーの点、10人の和=総点)
- 前回の未着手の案を同じ文で繰り返さない。重要なら「前回も挙げた。まだ未着手」と明記し、より小さく切った最初の一歩を書く
- 仕様変更を伴う案には「(仕様変更の提案)」と付ける
- 気づいた矛盾・片付け忘れ(ツールの目標値と仕様のずれ、作業ツリーの `.bak`・`tools/tmp_*`、未コミットの作業、
  セキュリティルールの緩さ、容量の見込み)は該当マスで必ず触れる
- 経緯の長話を書かない。事実・数字・出どころを短く

### 出さない案(ユーザーの方針)

クラス制・ヒーローパワー(装着式の能力を含む)・ローカライズ / 盤面での最適手の推奨(操作結果の予測の数字だけ可)/
裏方処理の成否の表示 / 英字のサブタイトル・キャッチコピー / 画像のUIクローム(コード描画のみ)/ 砂時計の絵の画像生成 /
安易な新しい常在キーワード・キーワードの組み合わせで量産したカード / 軽いデッキの息切れを消す引く効果 /
操作できるパネルのホバー詳細 / TODOへの「実機で確認する」項目。公開前の優先はUX、公開後はカードプール。
`docs/` と記憶にある最新の方針と食い違えば、そちらを優先する。

### 標準のレビュアーと観点(前回が無いときだけ)

レビュアー: A 初めてのカジュアル層 / B ランク・競技 / C 収集・継続層 / D ローグライト(遠征)/ E ゲームデザイナー /
F UI/UX / G アート・音・演出 / H プログラマ・TD / I 運営・マーケ / J データ・QA・アクセシビリティ。
観点は各レビュアーの立場に合わせて10個ずつ、独自性・中毒性・ゲーム性・わかりやすさ・操作感・見た目・継続性・公平性・対人・
技術品質のような幅を持たせて決める。

## 3. 検品して報告する(このセッション)

- 検算: 各レビュアーの和と総点。空欄のセル・一般論のセル・方針に反する案・仕様変更の印の付け忘れを直す
- 文書を `SendUserFile` で渡す(ページで見たいと言われたらArtifactにする)
- 完了報告は CLAUDE.md の順(判断待ち → 変えたこと → 見つけたこと → 確認できなかったこと)で。
  見つけたことにはレビュアー別の点の表(前回・今回)、上がった理由・動いていない数字・下がった理由、P0の項目を載せる。
  確認できなかったことには、実機を見ずに付けた見た目のマス、母数が小さい数字、確かめていない推測を挙げる
- P0に進むかはユーザーが決める。仕様変更の提案は承認までコードを書かない。進めるなら新しいセッションで
  「`scratchpad/reviews/Review_100points_YYYY-MM-DD.md` のP0から順に進めて」と始めるよう促す
