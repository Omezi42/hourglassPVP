# 26. Discordスラッシュコマンド

11章の募集通知・25章の日曜イベント告知が**ゲームからDiscordへ知らせる**ものであるのに
対し、こちらは**Discordから情報を取りに行く・見せ合う**向きの機能。公式Discordサーバーで、
ゲームを開かなくてもカードを調べたり、自分の構築やアカウントの状態を確認できるようにする。

## `/card <名前>`

- カードの表示名を部分一致で検索する。1件に絞れない場合は候補を一覧で示し、
  絞り込みを促す(実在する名前を入れたのに無反応に見える状態を避けるため)
- **表示名が完全に一致するカードがあれば、それを最優先で1件だけ返す。**部分一致だけで
  判定すると、「サンド」で調べたつもりが「サンドショット」も一致してしまい、
  1文字も略さず正確に打ち込んだのに候補選びを挟まれる(実際にユーザーがこれで
  詳細を見られなかった)。名前をそのまま正確に入力した人を最短で応答させるため、
  部分一致の絞り込みより完全一致を先に見る
- **結果は砂時計図鑑の詳細パネルを元に、Discord表示用へ最適化した1枚の画像として返す。**
  コスト・攻撃力・体力(砂術は「—」)・キーワード・効果の文・紋章を画像に収める
- **そのカードの能力の実演(9章「能力の実演」)を1周ぶん録った動画(MP4)を添える。**
  図鑑で動いている実演(本物の対局画面の切り抜き)をそのまま録るため、カードの演出も映る。
  複数の能力を持つカードは、全段を通した1周を1本にする。**都度その場で描画せず、
  カードを追加・変更したときに全カードぶんを静的な画像・動画として生成しておき、
  `/card`はそれを配るだけにする**。GIFでなくMP4にするのは、盤面の数字が読める大きさでもGIFの1/10程度に収まるため。
  埋め込みの画像欄は動画を再生できないので、動画はメッセージへ添付して送る
- 収録するのはプールにある全カード(トークンは除く。6章の「トークンはデッキに入れられず、
  一覧にも出さない」方針をそのまま引き継ぐ)

## `/deck <8桁のコード>`

- 9章のデッキコードをそのまま使う。コードを引き、**デッキの中身(30枚・コスト順)を
  画像として返す**
- **ゲーム内のデッキ表(9章)と全く同じ見た目の再現は求めない。**デッキ表はGodotの
  `SubViewport`描画に依存しており、Discord Bot側でその都度Godotを起動して再現するのは
  常駐サーバーを持たない方針(10章)と相性が悪い。**Discord Bot側(Node.js)で、
  コスト順に30枚のカード名・コスト・総量を並べた簡易な画像を独自に描画する。**
  真鍮の質感などの作り込みは持たず、中身が読めることを優先する
- 存在しないコードは「見つかりませんでした」とだけ返す(9章の共有パネルと同じ扱い)

## `/link` と `/profile`

- `/link` は引数を取らない。打つとDiscordの入力フォーム(モーダル)が開き、「ID」「パスワード」の2欄に
  **ゲームのログインに使うID/パスワード**を入れると、そのDiscordアカウントとゲーム内のuidを結びつける。
  ゲーム内に連携用の画面や番号は持たない(引数にすると打った文字列が入力欄に残るため、フォームで受ける)
- 確認はゲームのログイン(14章)と同じ認証で行い、**パスワードは保存も記録もしない**
- **ゲスト(未登録)のアカウントは連携できない。**ID/パスワードを持たないため、「ゲーム内のアカウント画面で
  IDを登録してから」と返す
- **失敗はDiscordアカウントごとに1時間5回まで。**認証の確認がすべて同じサーバーから出るため、1人の総当たりで
  全員の連携が止まらないようにする
- **1つのDiscordアカウントにつき1つのuidだけを保持し、結び直すと前の紐付けを上書きする**
- `/profile`(引数なし)を打つと、結び付いているuidの表示名・アイコン・称号・**砂金の
  残高**・オンライン対戦の通算成績を返す。**19章の戦績(CPU戦を含む通算)はローカル
  保存のためサーバー側から見えず、ここで返せるのは22章の`match_records`から集計できる
  範囲(オンライン対戦だけ)に限られる**。連携していない場合は`/link`を促す文言を返す

## カードスポットライト

- 毎日正午(12:00 JST)に、その日のカードを1枚紹介する投稿を自動で行う(#お知らせ)。
  日曜イベント告知・募集通知が深夜0時台に集中しているため、時間帯をずらしている
- **選び方は完全ランダムとし、直近30日以内に紹介したカードは候補から外す。**
  70枚(今後さらに増える)のプールであれば、1ヶ月ほどで自然と一巡する計算になり、
  特定のカードだけ繰り返し紹介される偏りを防げる。**候補が尽きた場合(直近30日で
  大半を紹介し終えた場合)は、その回だけ除外条件を外して全カードから選び直す**
- 25章の日曜イベント告知と同じCloud Schedulerの仕組みに乗せる

## デッキ紹介

ゲーム内の自分のデッキを、コマンドを打たずにボタンだけで #デッキ紹介 へ流す。スラッシュコマンドは
見つけにくいため、入口を常に見える場所に置く。

| チャンネル | 書き込み | 置くもの |
|---|---|---|
| #デッキを紹介する(入口) | Botだけ | 説明1行とボタン「デッキを紹介する」「アカウント連携」の投稿1件だけ(流れないようにする) |
| #デッキ紹介 | 誰でも | 人の書き込みと、Botが流す紹介の投稿 |

- 「アカウント連携」は `/link` と同じフォームを開く
- 「デッキを紹介する」を押すと、本人にだけ見える返事に**自分のゲーム内デッキの選択肢**を出す
  (30枚そろったものだけ・25件まで)。連携していなければ選択肢の代わりに「アカウント連携」ボタンを出す
- 選ぶと**コメント**のフォームが開く(省略可・200字まで)。送ると #デッキ紹介 へ2件流し、本人には
  「#デッキ紹介に投稿しました」とだけ返す
  - 1件目: 紹介した人(メンション)・デッキ名・コメント・デッキ表の画像(32章の共有リンクと同じもの)と、
    ボタン「ゲームに追加」「サイトで見る」(`/d/{デッキコード}`)
  - 2件目: 1件目への返信として**デッキコードの数字8桁だけ**(スマホのコピーが投稿単位のため。返信にして、
    間に人の書き込みが挟まってもどの紹介のコードか分かるようにする)
- デッキコードは紹介のたびに9章と同じ預け先へ発行する
- **攻略サイトからも紹介できる**(32章)。流す2件・コードの発行はDiscordから紹介したときと同じ
- **紹介はゲームの「みんなのデッキ」にも残す**(下記)。Discordを見ない人にも紹介されたデッキを届けるため

### みんなのデッキ(ゲーム内)

デッキ一覧のヘッダーの「みんなのデッキ」から開く画面。#デッキ紹介 に流れた紹介を新しい順に並べる。

- 1件の札に **デッキ名・紹介した人の表示名(ゲームの表示名。14章)・紹介した日・コメント(2行まで。超えたら「…」)・
  使っているカードのうちコストの高い5種の小さな絵**。新しい50件まで(それより古い紹介は出さない)
- 札を押すと詳細: デッキの30枚の棚(デッキ編集の棚と同じ見た目で、触れない)・コメントの全文・「デッキに追加」
- **「デッキに追加」はデッキ一覧の末尾へ新しいデッキとして足す**(名前は紹介のデッキ名)。足したら「『デッキ名』を追加しました」と1行。
  保存できるデッキの数が上限なら押せなくし、その旨を1行で示す
- 読み込めないときは「読み込めませんでした」と1行で示す。紹介が0件のうちは「まだ紹介されたデッキがありません」
- 紹介を消す操作はゲームにもサイトにも置かない(運営が消す)
- 「ゲームに追加」は、押した人が連携済みならその人の受け取り箱(32章)へデッキを入れ、
  「ゲームを開くと『デッキ名』が届きます」と本人にだけ返す。連携していなければ「アカウント連携」ボタンを、
  受け取り箱が埋まっていれば32章と同じ文言を返す。**ボタンに期限は無い**(中身はデッキコードとして預けてあるため)

## 応答の公開範囲

- **`/card` `/deck` `/link` `/profile` はいずれも、コマンドを打った本人にだけ見える
  応答(ephemeral)として返す**(`/link` のフォームを送った後の結果も同じ)。チャット欄が埋まっていくのを避けるためで、
  とくに`/profile`は自分のアカウントの状態を返すため、他人に見える必要が無い
- **カードスポットライトとデッキ紹介の投稿はこの対象外**とし、通常のメッセージとして全員に見える形で
  投稿する。コマンドの応答ではなく、コミュニティ全体へ向けた投稿であるため

## 実装方針(概要)

- カードデータは現状Godot専用の`.tres`にしかないため、書き出しの手順
  (`tools/export_web.sh`)にカードデータをJSON化して書き出す工程を足し、
  Cloud Functionsからも同じデータを読めるようにする
- **`/card`の画像・実演動画は、カードを追加・変更したときにまとめて生成しておく。**
  静止画・動画の撮影はいずれも実際にレンダリングしたピクセルを読む必要があり
  `--headless`実行では動かないため、`tools/export_web.sh`(全工程が`--headless`)には
  組み込まず、別のツールとして持つ。都度その場で描画する仕組みは持たない
- **`/deck`の画像だけは都度Discord Bot側(Node.js)で描画する。**組み合わせが
  無数にあり事前生成できないため、ここだけ動的生成が必要になる
- Discordの操作(スラッシュコマンド応答・自動投稿)はいずれも25章で導入した
  `discordInteractions`(HTTPS)・Cloud Schedulerの枠組みに追記する形で足し、
  **常駐するBotプロセス(Gateway接続)は導入しない**という既存方針は変えない
