## 2. 人が触って確かめること(実機確認)

ヘッドレスではGUIのクリックもホバーも届かず、演出の見え方も詰められない
(Architecture.md 11章)。**ロジックはいずれもヘッドレステストで押さえてあり、
ここに残っているのは「人の目でしか判定できないもの」だけ**。

### 1クライアントで確認できるもの

| 対象 | 見るところ |
|---|---|
| 対局中の演出 | 揺れの強さ・反転の行き過ぎ・破壊の破片。静止画では詰められない |
| カード詳細のホバー | 対局画面とデッキ編集。`hovered` / `mouse_exited` の配線と、消えるまでの猶予(0.15秒) |
| 時計工房・砂時計図鑑 | 駒のホバーと押下、段が多いときのスクロール、絵を押しての反転、語を押しての用語ポップ |
| キーワード辞書の実演 | 図版を紙の色にしたため、辞書の暗い背景の上で「紙に刷った図版を貼ってある」と読めるか |
| CPU戦の思考レベル | モーダルの表示・選択・対局への反映(上級の補正7項目すべて) |
| リーサルパズル | 操作と、エンドレスの難易度の手応え(`PuzzleGenerator` の `MIN_BRANCHING` 等はまだ初期値の見積もり) |
| デイリーミッション | 受取(残高が動く)。日をまたいで課題が入れ替わること |
| ショップ | 購入(残高が動く) |
| 反転権 | ボタン押下・対象選択・演出 |
| デッキ表の画像コピー | unityroomで `navigator.clipboard.write()` が通るか。断られたら右クリックコピーへ落ちるか。Xの投稿欄へ貼れるか |
| デッキコード | 発行したコードを別の端末で読み込めること |
| 砂時計の絵の1組化 | unityroomで読み込みが速くなっていること(pck 9.65MB → 3.13MB) |
| 日曜イベント | 日曜以外の日に日付判定だけ差し替えて動作確認 |

### 2クライアントが要るもの

| 対象 | 見るところ |
|---|---|
| ルームマッチ画面 | 参加コードのコピー、持ち時間を切った対局で双方とも時計が出ないこと、版違いの弾き方 |
| 切断からの復帰 | **保険の機能であり、動かなくても対局は成立する**ため優先しない |
| 対局の記録と分析 | 1局通して `match_records` が1件だけ残り、`stats/global` が1増えること |

### Discord側で確認するもの

- [ ] `/card` `/deck` `/link` `/profile` の4コマンドと、カードスポットライトの自動投稿。
      デプロイ・コマンド登録は完了済みで、**Discord上で実際に打つ作業だけが残っている**

## 4. バランスの測り直し(まとめて1回で行う)

**個別に測り直すと基準そのものが動いて無駄になる。**次にプールを触る回に、下記をまとめて行う。

- [ ] **カード1枚ごとの勝率(`docs/Hourglasses.md`)は、デッキ20枚・初期HP30時代の測定のまま。**
      枚数もHPも変わっているため前提が崩れている
- [ ] **35枚(50種化の27種 + マナカーブ調整の8種)と砂術12種は各400戦(誤差±5pt)でしか
      測っていない。**800戦で測り直す
- [ ] **先手勝率が54.8%、逆転率が38.6%**(目標45〜55% / 25〜35%)。**先に当たるのは逆転率**。
      手番の補正は引き続き足さない(効き幅が大きく、重ねると必ず行き過ぎる。GameDesign.md 7章)
- [ ] **初期HP24化で先手勝率が57〜60%まで上振れすることは承知のうえで採用した。**
      手番の補正(コイン維持・ヒーローパワー案)を検討する回に、あわせて調整する
- [ ] **CPUは砂術を持て余す**(BalanceReport_v5.md 10.6節)。1手ごとの貪欲法で1手番の
      マナ配分を見ないため、実測は砂術を過小評価している可能性が高い。人のプレイテストと突き合わせる
- [ ] 弱い砂術6枚を強めるかどうか。**強めた案と実測値は測定済み**(同10.2節)。
      **砂塵嵐(58.0%)は、はみ出したまま出すと決めてある**(ユーザー判断。調整漏れではない)
- [ ] 記録が貯まったら `tools/analyze_matches.py` を回し、シミュレーション値と突き合わせる
